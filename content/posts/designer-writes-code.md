我见过太多这样的对话：

> 设计："这不是我画的样子。"
> 开发："我按标注写的啊。"

两边都没说错。问题出在**设计稿是静态的，产品是动态的**。

## 一百米里有什么

一张精心绘制的卡片，在真实环境里至少会遇到这些情况：

- 标题有两行，甚至三行；
- 描述为空；
- 标签超过五个，换行后错位；
- 图片加载失败；
- 在 320px 宽的屏幕上；
- 用户开了大字号；
- 暗色模式下对比度不够。

设计稿通常只画了最理想的那一种。剩下的全靠工程师临场发挥，或者干脆没人管。

## 把状态也画进去

我的做法是：**任何组件，至少画四种状态。**

```text
┌─────────────┬─────────────┐
│  理想态      │  极端文案    │
├─────────────┼─────────────┤
│  空态        │  加载/失败   │
└─────────────┴─────────────┘
```

听起来工作量翻了四倍？其实不会。用 Figma 的变体（Variants）功能，复制一份改文字就行，十分钟能搞定。但这十分钟能省掉后面三轮返工。

## 间距比颜色更重要

如果只能统一一件事，我选间距系统。颜色错了只是不好看，间距错了整页都会散。

```css
/* 只用这几个值，不要出现 13px 这种数字 */
--space-1: 4px;
--space-2: 8px;
--space-3: 12px;
--space-4: 16px;
--space-6: 24px;
--space-8: 32px;
--space-12: 48px;
```

当设计师和工程师用同一套刻度说话，"这里感觉有点挤"就能翻译成"这里应该是 12 而不是 16"。

## 关于还原度

最后说一句可能不太受欢迎的话：**100% 还原度不是目标。**

浏览器里的字体渲染、滚动条、真实数据的长度，都和设计稿不同。追求像素级还原往往意味着写一堆 `margin-top: 13px` 的魔法数字，代码会迅速腐坏。

更好的目标是：**90% 还原 + 一致的设计语言 + 能扛住极端情况。** 剩下那 10%，交给一起对着屏幕微调的十分钟。
