`console.log` 当然能用，我自己也还在用。但它有三个绕不开的成本：

1. 它**留在代码里**。忘了删就是一次脏提交，删干净之后下次又得重写一遍。
2. 它**要重新构建**。热更新快也是几十秒，而你只是想看一眼中间那个值。
3. 最要命的是——它通常意味着你在**猜**。"我觉得问题可能在这一步"，于是打一个日志；不对，再往前打一个。

第三条才是关键。有效调试的分水岭不是用不用 `console.log`，而是：**先问清楚自己到底缺哪个信息，再挑工具。**

下面按"你不知道什么"分五类。

## 一、不知道某个值是什么

最常见的情况。但这里有个几乎没人用的东西，比 `console.log` 好得多：**logpoint（日志断点）**。

做法是：在 Sources 面板的行号上**右键 → Add logpoint**，然后像写 console 一样写内容：

```text
轮次 {i}，状态 {status}，耗时 {Date.now() - startedAt}ms
```

花括号里的表达式会被求值。它会在这个位置**打印一行日志**，但**不暂停执行**。

它强在哪：

- **不改代码**。你的源文件一个字符都不动，所以没有忘删的问题，也不会产生脏提交。
- **不用重新构建**。改 logpoint 等于改一行即时生效的配置。
- **在改不了的源码上也能用**。这是它最有价值的场景：线上环境的构建产物、压缩过的第三方脚本，你没有源码，但可以在 DevTools 里对着它下 logpoint。

用完在行号上右键清掉即可。

## 二、不知道它从哪一步开始变错

知道大概位置、但不知道是哪一次循环、哪个分支出的问题。这时候打日志会刷屏，用**条件断点**。

在行号上**右键 → Add conditional breakpoint**，写一个表达式：

```js
i === 87 && items[i]?.id !== expectedId
```

只有表达式为真时才停。于是你跳过了前面 86 次正常循环，直接站在出错的那一刻。

配合条件断点用的两个操作：

- **Watch（监视）**：把想看的表达式钉在侧栏，每停一次自动重新求值，不用反复手打；
- **Call Stack（调用栈）**：从当前帧往上逐帧点，每一帧都能看到自己的作用域变量。你想找的"是谁把它变成这样的"，往往在上面两三层。

如果连"哪一步"都不知道、只想知道"是谁在改它"，那可以用**属性断点**：在 Elements 面板里对一个 DOM 节点右键 → Break on → attribute modifications / subtree modifications。谁改的，栈就停在谁身上。

## 三、不知道谁在调用它

这类问题的传统做法是去源码里搜函数名、在函数第一行下断点。有更快的：

**`debug(fn)`——直接在 Console 里给函数下断点。**

```js
// 这个函数一被调用，就停在它的第一行
debug(handleSubmit)

// 调试完取消
undebug(handleSubmit)
```

不用打开源码文件、不用找到那一行。对于"这个函数到底被谁调的、参数是什么"这类问题，它是最短的路径。

**`monitor(fn)`——看调用序列和参数，但不暂停。**

```js
monitor(handleSubmit)
// 之后每次调用都会打印：
// function handleSubmit called with arguments: [{type: "submit"}, Event]

unmonitor(handleSubmit)
```

它和 `debug()` 的分工很清楚：**想看"调用了几次、参数分别是什么"用 `monitor`；想停下来逐步看用 `debug`。**

**`getEventListeners($0)`——看这个元素上到底绑了什么。**

```js
getEventListeners($0)
```

（`$0` 是你在 Elements 面板里当前选中的节点，见下一节。）

返回的是事件类型、是否只触发一次、以及**处理函数的引用**。最关键的一步：右键那个函数 → **Show function definition**，直接跳到源码里定义它的地方。当"这个按钮点了没反应 / 点了触发两次"时，这是定位最快的手段。

**`monitorEvents($0, ['click'])`——看它实际触发了哪些事件。**

```js
monitorEvents($0, ['click', 'mousedown'])
// 停止
unmonitorEvents($0)
```

第三个参数还能用 `'mouse'` 这样的通配。用它可以一眼看出"点一下到底触发了几个事件、顺序是什么"——事件冒泡和重复绑定这类问题，看一遍事件流就清楚了。

## 四、不知道接口返回对不对

后端还没好、或者想试一下"如果这个字段为空会怎样"，传统做法是起一个 mock 服务。不用。

**Override content——直接改掉这条请求的响应。**

在 Network 面板里找到那条请求，**右键 → Override content**。第一次用会提示你选一个本地目录用来存覆盖内容，之后这条请求的响应就会从本地文件读，你可以在文件里随便改。

改完刷新页面即可生效，想还原就删掉那个本地文件。用它来验证前端的空值处理、错误分支、超长文本，比等后端配合快得多。

同理还有两个"复制"操作，用来把线上的问题搬到本地复现：

- **Copy as fetch**：把这条请求复制成一段 `fetch(...)` 代码。粘进 Console 就能原样重放，还能顺手改参数试。
- **Copy as cURL**：复制成 curl。适合拿去别的地方（另一个终端、别人的机器、或者贴进 issue）复现。

另外有两个设置必须知道，否则你会误判：

- **Preserve log**：勾上之后，页面跳转和刷新**不会清空** Network 和 Console。排查"提交表单之后发生了什么"时，不勾就等于白看——因为记录已经被刷新清掉了。
- **Disable cache**：只在 DevTools 开着时生效。这解释了那个经典现象："我改了代码但样式没变"——其实是你自己开着 DevTools 所以命中不了缓存，而不开的时候命中缓存。

## 五、控制台里少打一半字

Console 里有一整套工具函数，用熟之后能省掉大量"复制粘贴到编辑器里看"的动作。

**`$0`：当前选中的节点。**

在 Elements 面板点一个节点，然后回到 Console 输入 `$0` —— 它就是那个节点。`$1` 到 `$4` 是之前选过的四个，可以往回翻。

配套的几个：

```js
$0.outerHTML          // 直接看结构
copy($0.outerHTML)    // 直接进系统剪贴板，不用手抄
inspect($0)           // 在 Elements 面板里跳过去选中它
```

**`$` 和 `$$`：选择器。**

```js
$('.card')      // = document.querySelector
$$('.card')     // = document.querySelectorAll，但返回的是真数组
```

`$$` 返回**真数组**是重点——它能直接链式调用：

```js
copy($$('.card').map(el => ({
  title: el.querySelector('.title')?.innerText,
  price: el.querySelector('.price')?.dataset.value,
})).filter(x => x.title))
```

把页面上所有卡片的标题和价格抓成一个 JSON，已经躺在剪贴板里了。写一次性抓取脚本时，这比先打开编辑器写 Playwright 快得多。

**`$_`：上一次的结果。**

```js
// 上一步算出了一个很长的数组，现在想把它存下来或复制走
copy($_)
```

**`queryObjects()`：找某类对象还剩多少个。**

排查内存泄漏或者"到底创建了几个实例"时有用：

```js
queryObjects(MyStore)   // 列出所有由这个构造函数创建、还没被回收的对象
```

还有两个减少噪音的：`table(obj)` 把对象转成表格（对象数组别再一个个展开了），`clear()` 清屏。

另外值得开一下 **Live Expression**（Console 面板右上角那只眼睛）：把一个表达式钉在那里，它会**持续重新求值**。想看某个状态变量的实时变化，不用反复手敲。

## 六、堆栈被第三方库淹了

点进调用栈，前二十层全是框架和库的内部函数，你自己的代码埋在中间。这时候**黑盒化**那个文件：

在 Sources 面板的调用栈里对着那个文件**右键 → Add script to ignore list**（旧版本里叫 Blackbox script）。

之后调试器会**跳过**这个文件：不在它里面停、调用栈里也折叠掉它的内部帧。于是栈里剩下的基本就是你的代码。

框架项目里我通常会黑盒掉：打包后的依赖 chunk、UI 库、以及那些永远不出问题的 polyfill。

## 后端（Node）那边也是同一套

浏览器上的这些东西，Node 端有对应的入口：

```bash
# 启动时暂停在第一行，等调试器连上来
node --inspect-brk ./src/server.js

# 不想一开始就停，只挂上调试器
node --inspect ./src/server.js
```

然后在 Chrome 里打开 `chrome://inspect`，点一下就能连上——**用的还是你熟悉的那个 DevTools 界面**，Sources、断点、调用栈、条件断点全都在。不用再学一套新的。

## 什么时候 console.log 仍然是对的

写这篇不是要把它判死刑。这几种情况下它确实更好用：

- **你需要看的是"序列"而不是"某一刻"**。比如一连串请求的先后顺序、生命周期钩子的触发顺序。一行行日志排下来，比反复暂停直观得多。
- **它得跨环境存在**。构建脚本、CI、别人的机器上——那些地方没有 DevTools 可以连。
- **它就是一次性的**。花两分钟就能确认的事，不值得为它配一套调试环境。
- **它要留痕**。排查偶发问题时，日志本身就是证据，而断点只能停在你能守在屏幕前的时刻。

判断标准还是那句：**先想清楚缺什么信息**。

- 缺"某一刻的值" → logpoint
- 缺"哪一次出的问题" → 条件断点
- 缺"谁调用的" → `debug()` / `monitor()` / `getEventListeners()`
- 缺"返回不对时前端会怎样" → Override content
- 缺"操作顺序" → 那就还是 `console.log`，认真打

上面提到的每个函数和菜单，都在 [Chrome DevTools 官方文档的控制台工具函数参考](https://developer.chrome.com/docs/devtools/console/utilities)里，可以对着核一遍。
