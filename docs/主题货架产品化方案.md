# 主题货架产品化方案

**目标**：把「未定义空间」这套博客变成「客户可选主题、你最少折腾交付」的可售卖产品。

**结论先行**：不要做「运行时一键换主题」。社区/官方模板是**完整站点**（自带布局、组件树、路由、配置），不是皮肤，互斥且塞不进同一个代码库。

**正确做法** = 内容契约 + 主题货架 + 代部署交付。

## 3. 架构约定（必须钉死的三条）

| 层 | 内容 | 是否可变 |
| --- | --- | --- |
| 内容层 | `content/*.md` — 客户的文字与图片 | 换主题时不动 |
| 配置层 | `app/data/site.ts` — 站名 / 作者 / 导航 / 社交 | 换主题时不动 |
| 主题层 | layouts · components · css | **唯一变量** |

**契约定义**：任何主题都必须能从 `content/*.md` + `app/data/site.ts` 读出全部内容。只要契约一致，客户感知到的就是同一件事——选一个、交内容、拿站。

### 主题来源两条路线，不要混用

- **路线 A｜Layer 化自研**：主题写成 Nuxt Layer，`extends: ['./themes/<name>']` 一行切换。真正的「一行换主题」，可长期维护、可收年费。**上限 3–5 套**，每套要亲手包。最小改造面 = 现有 `app/layouts/default.vue` + `app/components/site/`。
- **路线 B｜Fork 社区模板**：每个模板独立仓库，只对齐 content 与 site.ts 的契约。数量能起来，是小红书「有货」的底气。代价是每个是独立站，上游停更你兜底。

## 4. 授权核查（转售前必须过一遍）

| 已克隆主题 | 授权 | 可商用转售 |
| --- | --- | --- |
| bloggrify | MIT | 可以 |
| nuxt-theme-next | MIT（依赖 `@nuxt/ui` v4，免费开源，非 Pro） | 可以 |
| 2giosangmitom | MIT | 可以 |
| blog-v3 / clarity | `MIT OR CC-BY-NC-SA-4.0` 双授权 | **需处理**：代码可选 MIT，但仓库含作者自己的文章（`content/posts`），那部分是非商用。转售前必须清空对方 content，只保留布局代码 |
| nuxt-blog | package.json 写 MIT，但**仓库无 LICENSE 文件** | 有风险，建议先征询作者或规避 |
| the-green-chronicle / slantire | 依赖 Nuxt UI Pro（付费组件库） | 不可打包转售 |

**三种售卖形态的合规要求不同，先定形态再谈授权：**

| 形态 | 你在做什么 | 要求 |
| --- | --- | --- |
| 卖服务（我帮你搭好） | 使用开源主题产出成品站 | 最宽松，MIT 主题均可 |
| 卖模板（给源码，客户自己搭） | 在**分发**别人的代码 | 必须遵守其 license，MIT 要求保留版权声明 |
| 卖「可换主题的托管服务」 | 最接近 SaaS 再分发 | 最容易踩雷，需逐套确认 |

**推荐：卖服务。** 合规最宽松，且正好对应下面的交付方案。

## 5. 交付 SOP

目标：**单客户交付 ≤ 20 分钟**。

1. 客户看 demo 站选主题（3 个 demo 站链接，不是效果图）
2. 客户给内容（微信 / 飞书文档 / Word，不要求他碰 Markdown）
3. 你跑 `scripts/new-client.mjs <客户名> <主题名>`：生成 content 目录 → 填好 site.ts → 建仓库 → 配环境变量 → 触发部署
4. 交付：网址 + 一页「以后怎么发文章」说明

**客户操作降到「付款 + 发内容」两步。**

### 内容更新路径（按客户数递进）

| 阶段 | 方式 |
| --- | --- |
| 初期（≤10 客户） | 客户发给你 → 你或 Agent 转 md → push → 自动部署（已有 `scripts/new-post.mjs`） |
| 10 客户之后 | 上 Pages CMS / Decap CMS，Git 后端可视化编辑 |
| 任何时候都不该做 | 让客户自己写 Markdown 提交 Git |

## 7. 三步走

### 本周：先收第一笔钱，不写新代码
1. 拿已克隆的 3 套（clarity / bloggrify / nuxt-blog）各部署一个 demo 站，用真实内容
2. 把 `theme-compare` 改成客户视角：demo 链接 + 截图 +「¥xxx 帮你搭好，你只管写」
3. 发小红书。**先验证有没有人问价**——没人问说明问题在选题或渠道，不在主题数量

### 一个月：钉死契约，做交付 SOP
4. 写 `CONTRACT.md`：主题必须读 `content/posts/*.md` 与 `app/data/site.ts` 的哪些字段
5. 做 `scripts/new-client.mjs`，把单客户交付从半天压到 20 分钟

### 三个月：决定是否迁栈
6. 若客户在挑主题、抱怨选择少 → 迁 Astro（主题池几百个，且可买授权转售）
7. 若客户更在意省事 → 留 Nuxt，主题 4–5 套足够，精力放在交付速度

## 8. 待决问题

- 迁不迁 Astro？判断依据是「客户是否真的在挑主题」，不是你觉得主题少。
- 卖服务还是卖授权？建议先卖服务（合规宽松、可验证需求），后续再考虑授权。
- `blog-v3` 与 `nuxt-blog` 的授权需要处理或规避后才能进入货架。
